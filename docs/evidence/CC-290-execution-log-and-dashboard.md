- 항목: CC-290 (UNE-JNL-001~004)

- 마이그레이션: `0040_execution_log_projection.sql`,
  `0041_execution_log_review_fixes.sql`(이중검토 보정)

## 1. 무엇이 동작하는가

```
GET  /situations/{id}/dashboard?at=&runId=        전자상황판  (DASHBOARD_READ, 200)
```

**사실원장을 처음으로 읽는다.** 다섯 항목이 이벤트를 쌓는 동안 그것을 보는
경로가 하나도 없었다.

## 3. 착수 전에 측정한 것 — 이벤트 스트림이 KPI를 지탱하지 못했다

fable과 상의할 때 "KPI가 필요로 하는 상태 전이는 나열된 이벤트 타입으로 전부
덮인다"를 전제로 답을 받았다. **그 전제가 이 저장소에서는 거짓이었다.**

| 없던 것 | 재생에 미치는 영향 |
|---|---|
| 임무별 생성 이벤트(실행 단위 `taskCount` 요약만) | 어느 임무가 언제 생겼는지 알 수 없다 |
| 임무별 취소 이벤트(같은 형태) | 접힌 임무를 영원히 직전 상태로 본다 |
| **릴레이의 `TASK_SENT`** — 상태만 바꾸고 이벤트 없음 | 전파된 임무를 영원히 `CREATED`로 본다 |

셋째는 CC-280이 알림 전파에서 고친 것(0039 §1)과 **같은 계열**이다: 상태 변경이
사실원장 밖에서 일어났다. 그때는 감사 문제였고, 재생이 정본이 되는 순간
기능적 결함이 됐다.

셋 다 메운 뒤에 대시보드를 만들었다.

## 4. 판단한 것

### 4.1 판은 이벤트에서 계산된다 (D1)

CC-280이 임무에 수행 시각 컬럼을 두지 않은 것과 같은 결정이다. 대시보드만 임무
행을 정본으로 삼으면 그 결정을 배반하고, 두 정본이 갈라지는 날 어느 쪽이 참인지
말할 수 없다.

되돌리는 비용도 비대칭이다 — 임무 행 집계를 택하면 이벤트 완전성 압력이 사라져
그 기간의 과거가 **영구히** 복원 불가가 된다. 재생의 약점(성능)은 가역이다.

### 4.2 정정은 star다 (D4)

사슬이면 "지금 사실"에 답하려고 재귀를 따라가야 하고 중간 한 줄이 빠지면 답이
없다. star면 유효본이 O(1)이고 두 번 틀려도 답이 있다.

### 4.3 사람이 보고한 사실만 정정할 수 있다 (D7)

시스템 관측 이벤트는 "그때 그렇게 했다"는 기록이라 그 자체로 참이다. 시스템이
잘못했으면 기록을 고치는 것이 아니라 **새 조치**로 사실을 하나 더 만든다.
`status`는 어떤 정정으로도 바꿀 수 없다 — 허용하면 CC-280이 방금 고친 결함을
정정 경로로 다시 들여온다.

### 4.4 응답이 자기 근거를 밝힌다 (D10)

`provenance`가 이벤트 수·시간 축·임무 행에서 온 항목·잘림 여부·이벤트가 말하지
않은 임무 수·**재생과 임무 행의 어긋남**을 싣고, 화면이 그 문장을 판 위에 적는다.
숫자만 주면 화면이 그것을 완전한 사실로 읽는다.

## 5. 증명한 규칙

- **판이 이벤트를 따른다**: 임무 행을 `COMPLETED`로 직접 바꿔도 판은
  `ACKNOWLEDGED`를 말한다(D1의 시험).
- **`at`이 그 시점을 낸다**: 수신확인 전 시각으로 물으면 `awaitingAck=1`,
  지금 물으면 `inProgress=1`.
- **릴레이가 사실원장에 남긴다**: 전파 후 `TASK_SENT` 이벤트 1건, payload에
  `status: 'SENT'`.
- **정정이 원본을 고치지 않는다**: 원본 payload 그대로, 정정 1건, 유효값은
  정정본이고 건드리지 않은 값도 완성본에 남는다.
- **정정의 정정은 409**, 그러나 **원본을 다시 정정하면 그것이 유효본**이 된다.
- **시스템 관측 이벤트 정정은 409**(`EXEC-409-001`).
- **`status` 정정은 거부**되고 위반 항목이 `replacementFields.status`로 나온다.
- **원본은 어떤 경로로도 바뀌지 않는다**: 직접 UPDATE가 42501.
- **타임라인이 원본을 감추지 않는다**(UNE-JNL-002와 대시보드 `recentEvents`
  둘 다): 원본이 목록에 남고 `correctedBy` 표시만 달리며, 정정 이벤트도 한
  줄로 보인다.
- **정정해도 임무 상태가 되돌아가지 않는다**: 완료된 임무의 과거 진행보고를
  정정해도 `completed`가 그대로다.
- **실제 응답이 계약을 만족한다**: `DashboardView`·`ExecutionEventPage`·
  `ExecutionEventDetail`·`ExecutionEvent`를 Ajv 2020-12로 검증한다.
- **판이 자기 결손을 드러낸다**: 사실원장을 건너뛴 상태 변경을 만들면
  `provenance.divergences`에 그 임무가 실린다.
- **진행률도 재생에서 온다**: 임무 행의 진행률을 바꿔도 판은 이벤트를 따르고,
  `statusEventId`로 그 근거 이벤트에 닿는다.
- **실행 스코프에서 취소 이벤트가 빠지지 않는다**(payload에 `runId`가 없어도).
- **과대 본문은 413**, 과대·과중첩 정정 값은 409.
- **필터**: 종류·애그리거트로 실제로 좁혀진다.
- **잘못된 조회**: `at=어제` → `DASH-8001`, from>to → `EXEC-8002`.
- **경계**: 타 기관 판은 `SIT-404-001`, 타 기관 이벤트 상세는 `EXEC-404-001`,
  현장 담당자의 정정은 403.

## 6. 남은 조건

ADR-43 수용 한계 16개가 정본이다. 특히:

1. **자동갱신이 SSE가 아니라 폴링이다**(10초) — 상황 단위 SSE 엔드포인트가
   설계 10에 없다. 화면이 주기와 마지막 이벤트 시각을 밝힌다.
2. **기한만 이벤트가 아니라 임무 행에서 온다** — 기한 변경이 이벤트로 남지
   않아 **과거 시점 조회에도 현재 기한이 쓰인다**. `provenance`가 그것을 밝힌다.
3. **`recordedAt` 축을 지원하지 않는다** — 늦은 보고가 있으면 "그때 화면에
   있던 것"과 다르다.
4. **재생이 O(이벤트 수)다** — 느린 것이 측정되면 그때 캐시를 넣는다.
5. **정정에 승인 절차가 없다** — 권한만 있으면 바로 기록된다(감사에는 남는다).
6. **`TASK_CREATED`가 세 뜻으로 쓰인다**(전파 접수·임무 생성·실행 요약) —
   사실원장은 append-only라 지난 이벤트의 타입을 바꿀 수 없다.
7. **페이지를 쪼개면 `correctedBy` 배지를 잃는다** — 정본은 상세다.
8. **정정 값의 의미를 검증하지 않는다**(길이·깊이만) — 타입별 필드 화이트리스트가
   다음 단계다.

## 7. 이중검토에서 고친 것

`architecture-guardian`(HIGH 3·MEDIUM 5·LOW 5)과 `qa-gate-reviewer`(FAIL 3)가
찾은 것 중 실제 결함:

| 무엇 | 왜 위험했나 | 어디서 닫았나 |
|---|---|---|
| 정정이 fold에 새 관측으로 섞였다 | **완료된 임무가 진행으로 되돌아간다** | D12 |
| 계약 스키마가 어떤 응답으로도 만족될 수 없었다 | allOf + `additionalProperties:false`(ADR-24 D4를 밟았다) | 스키마 평탄화 + walker + 실응답 Ajv |
| `recentEvents`가 원본을 감추고 해시를 어긋나게 냈다 | D9의 위변조 신호가 무력 | D12 |
| `TASK_CANCELLED`에 `runId`가 없어 실행 스코프에서 탈락 | 접힌 임무가 영원히 직전 상태 | D13 |
| 과대 본문이 500 | 요청 문제를 서버 결함으로 답했다 | 전역 상한 + 413 |
| 동시 정정이 서로를 삼켰다 | 먼저 기록된 값이 사라진다 | D15(자문 잠금) |
| 워커 INSERT가 테이블 전체 | 워커가 정정 이벤트를 넣을 수 있었다 | D16(0041) |
| 릴레이가 이벤트 없이 성공을 반환 | 방금 고친 결함의 예비 경로 | 예외로 롤백 |
| `ix_execution_event_fold`를 아무도 안 썼다 | 최대 볼륨 테이블에 쓰기 비용만 | 0041에서 교체 |
| 중복 FK·인덱스(0007과) | 검사 두 번, 지연성 불일치 | 0041에서 정리 |
| 정정 값에 길이·깊이 제한 없음 | append-only라 나중에 마스킹도 삭제도 못 한다 | 도메인 검증 |
| 정정에 확인 단계 없음 | 되돌릴 수 없는 조작인데 한 번 누르면 끝 | 화면 확인 단계 |
| `progressPct`가 임무 행에서 샜다 | 과거 판이 오늘의 진행률을 보여 준다 | 재생으로 |
| KPI→이벤트 drill-down 부재 | "미수신 3건"의 근거로 갈 길이 없다 | `statusEventId` |
| ADR이 없는 e2e를 있다고 적었다 | 문서가 실제보다 강한 보증을 말했다 | D14 + 실제 시험 |
| 배경 서술 2건이 사실과 다름 | 0007이 이미 만든 인덱스·FK | 문장 수정 |
