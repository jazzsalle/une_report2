## 3. 판단한 것

### 3.1 서명링크를 만들지 않았다 (D1)

설계 09가 `/task/:signedToken`을 적지만 **지금 그 링크를 배달할 수단이 없다** —
SMS·이메일·푸시가 전부 시뮬레이션이고 수신자 주소를 저장하지도 않는다(ADR-41).
사용자가 0명인 bearer 인증 경로는 공격면만 있다. 설계 10(우선순위 3)이 이
API들의 권한을 `TASK_ASSIGNEE`/`TASK_SUPERVISE`로 적고 있어 문서 우선순위로도
이쪽이 이긴다.

되돌리는 비용이 비대칭이다: 나중에 더하는 것은 **추가**이고, 지금 만들었다가
실제 채널 계약이 다른 모델을 요구하면 살아 있는 인증 경로의 **철거**가 된다.

### 3.2 담당자 확인이 두 계층이다 (D2)

`TASK_ASSIGNEE`는 여러 현장요원이 함께 갖는 역할이라 그것만으로는 "이 임무를 할
사람"이 되지 않는다. 서비스가 본인을 먼저 보고, 전이는 조건부 UPDATE로 실행된다 —
담당자 경로는 `WHERE status AND assignee_user_id`, 지휘자 경로는 `WHERE status`
(지휘자는 담당자가 아니어야 정상이다). 0행이면 `TASK-409-010`이다.

### 3.3 관측되지 않는 상태를 넣지 않았다 (D4)

설계 09 Task 상태표 열하나 중 셋을 뺐다.

| 값 | 이유 |
|---|---|
| `DELIVERED` | 수신영수증을 주는 채널이 없다(OB-06) |
| `REJECTED` | 반려하는 **순간** IN_PROGRESS가 된다 — 상태가 아니라 전이다 |
| `REASSIGNED` | 재배정하면 새 담당자의 SENT가 된다. "기존담당 읽기전용"은 보는 사람 기준의 화면 표시다 |

뒤의 둘은 `task_event`로 남고 화면이 마지막 이벤트에서 배지를 그린다.

### 3.4 수행불가로 남은 임무가 있으면 실행을 끝내지 않는다 (D9)

그것을 "끝났다"로 세면 아무도 하지 않은 절차 단계가 완료된 실행 안에 조용히
남는다.

### 3.5 오프라인 대기열의 보장은 한 줄이다 (D11)

**멱등 키를 넣을 때 한 번 만들고 재시도에서 그대로 쓴다.** 재시도마다 새로 만들면
복구 뒤 같은 보고가 여러 건 들어간다 — 설계 09 인수기준 "네트워크 복구 후 중복
없이 동기화된다"의 전부가 이것이다. 그리고 화면은 "대기 중"이라고 적는다.
보냈다고 표시하면 사람이 지휘소가 알고 있다고 믿는다.

## 4. 증명한 규칙

- **한 줄 흐름**: 수신확인 → 착수 → 진행보고 → 완료 → 승인. 진행보고는 상태를
  바꾸지 않고 완료 승인은 진행률을 100으로 굳힌다.
- **원자성**: 전이 셋에 임무 이벤트 3 · 사실원장 3 · 감사 3이 함께 남는다.
- **append-only**: `task_event`·`task_assignment` 모두 UPDATE가 42501로 막힌다.
- **담당자 아님**: 권한이 있어도 `TASK-403-001`(앱 계층 가드). 별도 시험이 가드와
  UPDATE 사이에 **상태**가 바뀌는 창을 만들어, 낡은 요청이 조용히 통과하지 않는
  것을 확인한다(201 또는 409, 중간 상태 없음).
- **알림은 임무를 움직이지 않는다**: `CREATED` 임무를 Escalation하고 릴레이를
  끝까지 돌려도 임무가 `CREATED`에 남는다(전파 종류 `ESCALATION`/`TASK_NOTICE`).
- **선행조건**: 멈춘 실행 `TASK-412-002`, 담당자 미배정 `TASK-412-003`.
- **끝난 임무**: 승인·반려·재배정·Escalation이 각각 `TASK-409-004/005/006/007`.
- **값 검증**: 진행률 140 → `TASK-422-006`, 없는 Escalation 대상 → `TASK-422-011`.
- **이력**: 각 이벤트가 **자기 시점의** 상태를 말한다(현재 상태가 아니다).
- **타 기관 파일**: 검사를 통과했어도 다른 기관 파일은 `FILE-422-003`.
- **중복**: 같은 멱등키 재전송은 재생(이벤트 1건), 다른 요청의 중복 수신확인은
  `TASK-409-001`, 승인 뒤 재제출은 `TASK-409-008`.
- **순서**: 수신확인 없이 착수하면 `TASK-409-002`.
- **완료조건**: 미충족 항목과 증빙 부족이 각각 위반으로 나오고(`TASK-422-008`)
  상태가 그대로다. 조건을 적지 않은 SOP도 빈 완료보고를 받지 않는다.
- **반려**: IN_PROGRESS로 되돌아가고 마지막 이벤트가 `COMPLETION_REJECTED`이며
  Outbox에 알림이 쌓인다.
- **재배정**: 새 담당자의 SENT, 이력 2행, 옛 담당자는 403 새 담당자는 201.
  없는 사람에게는 `TASK-422-010`.
- **실행 종료**: 앞 임무가 끝나면 다음이 활성화되고, 마지막 승인에서
  `sop_run.COMPLETED` + `ended_at` + `RUN_COMPLETED` 이벤트 1건. 수행불가가
  남으면 RUNNING을 유지한다.
- **알림 수신자**: 수행불가는 지휘자에게 가고 담당자에게는 가지 않는다.
- **훈련**: EXERCISE 실행의 반려는 전파를 만들지 않는다.
- **첨부**: `scan_status != CLEAN`이면 `FILE-422-003`, 같은 파일 두 번은 1건.
- **경계**: 목록은 내 것만, 타 기관 상세는 `TASK-404-001`, 현장 담당자에게
  감독 권한 없음(403).

## 5. 남은 조건

ADR-42 수용 한계 12개가 정본이다. 특히:

1. **서명링크로 임무를 열 수 없다** — 현장 담당자는 로그인해야 한다(OB-06 대기).
2. **알림은 여전히 아무 데도 가지 않는다**(ADR-41 수용 한계 1 그대로).
3. **최초 배정 경로가 약하다** — `assignee_user_id`를 채우는 API는 재배정뿐이다.
   역할규칙 해석이 오면 전파와 이어진다.
4. **미완료 임무 일괄 처리가 없다** — 상황 종료의 `openTaskPolicy`(CC-320) 자리다.
5. **현장 앱에 자동 새로고침이 없다** — 반려를 다음 조작 때 알게 된다.
6. RLS 커버리지 목록에 **8개**가 남았다 — `task_attachment`를 닫아 실행·전파
   계열은 전부 끝났고, 남은 것은 일지·평가 계열과 IAM 세션이다.
7. **현장 앱 로그인이 mock SSO뿐이다**(OB-01). 화면이 그 사실을 먼저 말한다.
8. **SCR-TASK-002·003의 화면 상당수가 없다** — 지휘자 조작은 API로만 가능하다.

## 6. 이중검토에서 고친 것

`architecture-guardian`·`qa-gate-reviewer`가 찾은 것 중 실제 결함이었던 것:

| 무엇 | 왜 위험했나 | 어디서 닫았나 |
|---|---|---|
| 알림 전파가 임무를 `SENT`로 만들었다 | 지시가 안 나간 임무가 "전파됨"이 되고, 그 전이가 사실원장 밖에서 일어났다 | 0039 §1 `TASK_NOTICE` + 릴레이 필터 |
| `advanceRun`이 실행을 잠그지 않았다 | 동시 승인 시 모든 임무가 끝났는데 실행이 `RUNNING`에 갇힌다 | `FOR UPDATE` |
| 0036 종료 트리거가 `COMPLETED`를 몰랐다 | 두 번째 방어선 상실 | 0039 §2 |
| 계약의 `SopRun.status`에 `COMPLETED`가 없었다 | 서버가 계약을 위반하는 값을 냈다. **그것을 잡던 단언을 내가 지웠다** | 계약 + 단언 복원 |
| SSE 공개 어휘에 `RUN_COMPLETED`가 없었다 | 실제로 나가는 프레임을 계약이 몰랐다 | 계약 + 양방향 게이트 |
| 이벤트 이력이 전부 현재 상태를 달고 나왔다 | "그때 무엇이 됐는가"에 거짓을 답했다 | 기록 시점에 상태를 굳힘 |
| 화면이 `requiresEvidence`를 몰랐다 | 제출 버튼을 열고 서버가 422 — 미리 거르는 목적이 무력 | `completionBlockers` |
| 오프라인 큐가 누를 때마다 새 키를 만들었다 | 재입력 중복을 못 막고 진행보고가 두 번 기록된다 | `findPending` 재사용 |
| 401을 "거절"로 다뤘다 | 세션 만료 상태로 앱을 열면 밀린 보고가 통째로 버려진다 | 401은 대기 유지 |
| 저장소가 테넌트를 RLS에만 맡겼다 | 정책 하나가 드롭되면 격리가 사라지는 단일 방어선 | 명시적 부모 조인(ADR-21) |
| 첨부 정책이 파일 테넌트를 안 봤다 | 같은 종류의 단일 방어선 | 0039 §3 |
| `geo`가 형태 없는 임의 JSON이었다 | 개인 위치정보에 최소화가 없었다 | `{lat,lon}` + 5자리 |
| ADR·증거가 e2e가 증명하지 않은 것을 적었다 | 문서가 실제보다 강한 보증을 말했다 | 문장을 사실로 낮추고 시험 추가 |

반론 하나: 검토가 "`SENT`를 연 것은 0038"이라 했으나 사실이 아니다 —
`0037_outbox_relay_and_dispatch.sql`이 `ck_task_status`를 `SENT`까지 넓혔다.
