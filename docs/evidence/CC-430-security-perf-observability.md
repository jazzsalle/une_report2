## 1. 보안 전수 매트릭스

지금까지의 보안 시험은 항목마다 한두 경로를 골라 막히는지 봤다. 증명하지 못한
것은 **아무도 고르지 않은 경로**다.

`listRoutes(app)`가 **런타임 라우터가 등록한 것 전부**를 준다. 소스를 정규식으로
읽으면 적힌 것만 보이고, 모듈에 넣지 않은 컨트롤러나 조건부 등록은 보이지 않는다.

| 질문 | 결과 |
|---|---|
| ① 토큰 없이 401인가 | **전수 통과** |
| ② 권한 없이 403인가 (본문 검증보다 먼저) | **전수 통과** |
| ③ 남의 기관 UUID로 2xx가 나는가 | **없음** |
| ④ 멱등 키 없는 POST | 6건, 전부 대체 보호 있음 |
| ⑤ 권한 선언 없는 라우트 | 2건, 전부 의도됨 |

④의 6건은 사유와 함께 고정했다.

| 라우트 | 왜 멱등 키가 아닌가 |
|---|---|
| `POST /auth/logout` | 본래 멱등 — 폐기된 토큰을 다시 폐기해도 같다 |
| `POST /plans/:id/context-drafts` | 계획서당 초안 하나(`uk_plan_context_draft_plan`). 재전송은 upsert |
| `POST /documents/:id/changesets` | `If-Match` + `baseRevisionId` 낙관 잠금. 두 번째 적용은 409 |
| `POST /documents/:id/revisions/:rid/restore` | 같은 낙관 잠금 |
| `POST /documents/:id/autosaves` | 고빈도 last-write-wins. 멱등 키를 걸면 저장이 막힌다 |
| `POST /sops/:id/validate` | 조회성 — 보고서를 낼 뿐 상태를 바꾸지 않는다 |

**목록은 양방향으로 본다.** 새 라우트가 빠지면 걸리고, 사라진 라우트의 예외가
남아도 걸린다. 실제로 ⑤에서 내 추측 둘이 그 자리에서 틀렸다 — `/auth/refresh`는
`@Public`이고 `GET /tasks`는 권한이 있다.

## 3. 관측성

| 무엇 | 이전 | 지금 |
|---|---|---|
| 로그 | 흩어진 `console.*` | JSON 한 줄, 상관관계 ID·테넌트·사용자·경로·상태·소요 |
| 가림 | 각 호출 지점 | **나가는 길목에 한 번만** — 이름으로 지우고, 본문은 크기만 |
| 메트릭 | 없음 | `une_http_requests_total`, `une_http_request_duration_ms`, `une_errors_total` |
| health | 언제나 `ok` | `live`(의존성 안 봄) / `ready`(DB·저장소 실제 점검 + 사유) |

실측으로 고정한 것.

- **저장소를 죽이면 `ready`가 `degraded`를 낸다.** 늘 `ok`인 health는 이 시험을
  통과하지 못한다 — 그것이 이 단언의 목적이다. DB는 여전히 `ok`로 남는다(하나
  죽었다고 전부를 실패로 적으면 어디가 문제인지 말하지 못한다).
- **메트릭 라벨에 자원 UUID가 새지 않는다.** 두 개의 UUID로 요청을 보낸 뒤
  `/metrics` 본문에 그 문자열이 없는지 본다. 새면 요청마다 시계열이 생기고,
  외부에서 수집기 메모리를 늘릴 수 있다.
- **로그에 비밀이 남지 않는다.** 토큰·비밀번호·자격증명·`authorization`은
  `[redacted]`, 본문은 `[N bytes omitted]`. 지우지 말아야 할 것(사용자 ID·
  상관관계 ID·중첩된 평문 필드)은 남는다 — 전부 지우면 로그가 쓸모없다.

`prom-client` 같은 런타임 의존은 더하지 않았다.

## 4. 백업·복구 훈련

```
[0/5] 도구 pg_dump 16 · 서버 16 (컨테이너 une-postgres 경유)
[1/5] 마이그레이션 50 · 테이블 69 · 정책 81 · 트리거 36
[2/5] 덤프 521292 bytes · 0.39s
[3/5] 복구 21.89s (RTO 합계 22.28s)
[4/5] 스키마·정책·트리거·행 수 전부 일치
BACKUP/RESTORE DRILL: PASS
```

**첫 실행이 결함을 잡았다.** PATH의 `pg_dump` 18로 서버 16을 덤프하면 덤프에
`SET transaction_timeout`이 들어가고 복구가 첫 줄에서 죽는다. 대조가 없었다면
"덤프는 떴다"로 끝났을 자리다. 버전 선검사를 넣어 시작 전에 멈추도록 했다.

대조 항목: 마이그레이션·테이블·컬럼·RLS 켜짐·FORCE·정책·트리거·인덱스·CHECK·FK,
그리고 전 테이블 행 수 지문. 보고서는 `docs/evidence/CC-430-backup-drill.json`.

## 6. 남긴 것

ADR-48 수용 한계 여섯. 특히:

1. **트레이스가 없다** — 수집기 주소가 OB-14에 딸려 있다. 상관관계 ID와 경로
   라벨이 이미 서 있으므로 수집기가 생기면 내보내는 쪽만 붙이면 된다.
2. **RTO는 거의 빈 DB 기준이다** — 실 데이터량에서 다시 재야 한다.
3. **오브젝트 저장소는 훈련 대상이 아니다** — 복구본은 메타데이터만 온전하다.
6. **워커 로그가 아직 `console.*`이다** — 로거는 공개했으나 이 항목에서 바꾸지
   않았다. 잡 실패를 상관관계로 추적하려면 후속이 필요하다.
