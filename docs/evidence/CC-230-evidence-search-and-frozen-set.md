## 2. 핵심 결정 넷

### 2.1 화면 흐름 상태를 저장하지 않는다

US-SIT-011은 아홉 개 상태를 말하지만 저장하는 것은 `DRAFT`/`FROZEN` 둘이다.
`SEARCHING`은 HTTP 요청이 진행 중이라는 뜻이라 요청이 끝난 뒤 그 행이 무엇을
뜻하는지 말할 수 없고, `NO_RESULTS`는 항목 0건인 DRAFT이며,
`EVIDENCE_CONFLICT`는 항목에서 계산되는 파생값이다. ADR-36 D1이
`knowledge_document`에서 한 판단과 같고 출발점도 같다(0004의 어휘 없는 컬럼).

계약 게이트가 이 결정을 지킨다 — 화면 전용 상태가 enum에 새어 들어오면 실패한다.

### 2.2 검색은 동기다

설계 10 §7.25 7단계의 "Worker가 호출한다"는 모든 화면 시퀀스에 붙는 공통
문구다. 판단 근거는 US-SIT-011이 **대화형**이라는 것(3단계 변환 → 4단계 선택)과
설계 08 §1.14의 **30초·1회**다. CC-220 업로드(60초 + 비동기)와 갈리는 지점이고,
그래서 이 경로는 워커 권한을 요구하지 않는다.

### 2.3 authorization filter는 응답 쪽에 있다

요청에 `doc_ids`로 범위를 주더라도 **저쪽 필터가 지켜졌는지는 응답을 봐야
안다.** 방어가 세 겹이다.

```
요청 범위 지정 (doc_ids)            ← OB-13/CR-UNI-008로 지원 여부 확인 중
도메인 checkEvidenceItem            ← 우리 목록에 없거나 자격 없으면 버린다
FK evidence_item → knowledge_document ← 앞의 둘이 뚫려도 DB가 23503으로 거부
```

버린 수는 `rejectedChunkCount`로 응답에 싣는다 — 조용히 버리면 사용자가
"왜 근거가 적은가"를 알 수 없다.

### 2.4 동결 후 불변

`evidence_set`과 `evidence_item` 양쪽에 트리거를 건다. 항목 쪽은
INSERT·UPDATE·DELETE 모두를 본다 — 근거가 하나 늘어도 "그때 무엇을 근거로
만들었는가"가 달라진다. `une_app`에서 UPDATE를 회수할 수는 없다(DRAFT를
고치는 것이 정상 흐름) — 0027/0029가 provider 원문에 쓴 것과 같은 행 단위
방식이다.

## 3. 작업 중 드러난 것

### 3.1 두 테이블에 RLS 정책이 한 번도 없었다

착수 시점 실측: `evidence_set`·`evidence_item`에 정책이 0건이다. 0011이
`une_app`에 전 테이블 DML을 일괄 부여하므로 **정책 없는 테이블 = 전 테넌트
공개**였고, CC-230이 첫 쓰기 경로를 여는 순간 격리가 깨질 상태였다. 0023이
상황 계열에서 발견한 것과 같은 자리다.

### 3.2 0004에 없어서 새로 넣은 것 둘

- **`frozen_at`/`frozen_by`** — 만든 사람과 동결한 사람을 구분할 수 없었다.
  US-SIT-011의 주 행위자가 "SOP 편집자, 통제관" 둘이므로 검토자가 만들고
  통제관이 동결하는 흐름이 기록되지 않는다.
- **`evidence_item.is_selected`** — 선택 여부를 담을 곳이 없어 **제외하려면
  지우는 수밖에 없었다.** 지우면 "무엇을 보고 제외했는가"가 사라지고
  A-02(공식 매뉴얼과 충돌 시 사용자 결정)의 근거가 남지 않는다. 후보 행은
  남기고 선택만 끄되 제외에는 사유를 필수로 걸었다.

### 3.3 mock 설계를 고쳤다

검색이 mock 내부 등록부에 있고 READY인 문서만 돌려주고 있었다. 그러면 mock을
통해 업로드하지 않은 테스트(API e2e는 문서를 DB에 직접 넣는다)에서 항상 0건이
되고, 더 근본적으로 **자격 판정이 두 곳에 생긴다** — 호출부가 이미
`isEvidenceEligible`로 거른 목록을 포트가 다시 판정하는 것은 역할이 아니다.
받은 목록을 그대로 쓰도록 바꿨다.

### 3.4 CC-220의 함정을 미리 피한 자리

검색이 실패해도 **잡과 원문은 커밋한다.** 트랜잭션 안에서 던지면 롤백되어
실패한 호출의 추적이 사라진다 — CC-220에서 거부 감사가 정확히 그렇게 사라졌고
QA 검토가 그것을 잡았다. 여기서는 실패를 결과값으로 들고 나와 밖에서 던진다.

## 5. 사내 개발자 요청 — CR-UNI-008 신설

`contracts/openapi/uni-knowledge-api-change-request-v1.yaml`에 `/search/`를
추가했고(예제 10건 계약검증 통과) 설명서 §7에 배경을 적었다.

핵심 질문은 **문서 범위 지정**(`doc_ids`)이다. UNE는 여러 기관 자료를 한
시스템에서 다루므로 A기관 SOP에 B기관 자료가 섞이면 안 된다. 지원되지 않아도
UNE는 동작하지만(응답을 다시 대조하므로) `top_k=8`로 요청해 절반이 남의
자료면 근거가 4개만 남는다 — 서로에게 낭비다.

응답 쪽 미확인 셋: 결과 배열을 감싸는 필드명, chunk 식별자 필드명(설계에도
없다), score 척도.

## 6. 이 항목이 닫지 않은 것

ADR-37 수용 한계 7건이 정본이며 그중 운영에 직접 걸리는 셋:

1. **PII 최소화가 완전하지 않다.** 주민번호·전화·이메일의 명백한 형태만
   가린다. **자유 서술의 성명·주소는 그대로 UNI로 나간다** — "신고자는
   홍길동입니다"는 가려지지 않으며 그 한계를 도메인 테스트로 고정했다.
   질의 구성 화면이 사용자에게 이 점을 알려야 한다.
2. **실 UNI `/search/`가 검증되지 않았다**(OB-13). mock이 검증하는 것은
   UNE 쪽 상태기계뿐이다.
3. **참조요약 폴링이 또 미뤄졌다.** ADR-36 수용 한계 2가 "CC-230에서 근거와
   함께 온다"고 적었으나 이번에도 닫지 않았다 — 근거 검색이 참조요약 없이
   성립하고 그 값을 소비하는 곳이 아직 없다. **CC-240으로 다시 넘긴다.**
   두 번 미뤘다는 사실을 여기 남긴다.

### 검토가 잡은 것 (전건 반영)

이중 검토에서 **BLOCKER 2건**이 나왔고 둘 다 실측으로 재현한 뒤 닫았다.

1. **`filters`가 UNI 요청을 덮어썼다.** `...input.filters`가 전개 마지막이라
   사용자가 `{"doc_ids": []}`를 보내면 범위 제한이 사라졌다. 응답 청크는
   걸러지지만 **원문은 걸러지지 않아** 남의 기관 문서 본문이 요청자 테넌트의
   `provider_result`에 적재된다. `minimizePii`도 우회됐다. CR-UNI-008에
   `filters`가 정의돼 있지 않으므로 **아예 보내지 않기로** 했다.
2. **동결된 집합을 지울 수 있었다.** 집합 트리거가 UPDATE 전용이라 부모를
   지우면 cascade가 근거를 데려가고, 자식 가드는 부모가 사라져 NULL을 읽고
   통과했다. DELETE 가드 + fail-closed + `REVOKE DELETE`로 닫았다.

그 밖에 고친 것: `score numeric(8,6)` 오버플로가 원문까지 롤백시켰고(수용
한계 7 정정), Snapshot 기준선에 30초 TOCTOU 창이 있었으며, 종료된 상황에도
근거를 모을 수 있었고, 412가 계약에 선언되지 않았고, `searchEvidence`
capability가 미등록이었다. UNI 실패 경로 테스트도 없었다(mock에 시나리오 추가).

그 밖에: A-02 충돌 탐지 없음(기관 KB 승격 워크플로 부재에 묶여 있다),
근거 선택·제외 API 없음(설계 10에 오퍼레이션이 없다 — 화면이 붙는 시점에
변경요청), EvidenceSet 보존기간 없음, `score` 범위 미검사.
