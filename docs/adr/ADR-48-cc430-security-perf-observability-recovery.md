# ADR-48 — CC-430: 보안·성능·관측성·백업복구

- 상태: 채택
- 작업 항목: CC-430 (G6)
- 결정: D1~D6, 수용 한계 6
- 관련: ADR-32 D3(검증과 검사의 축 분리), ADR-35 D2·D4(롤 경계),
  ADR-43 D1(집계는 한 산출기에서), ADR-47 D4(마이그레이션이 자기 일을 확인한다)
- 마이그레이션: 없음
- 선행 항목의 의존성 해석: MASTER_WORK_ITEMS는 CC-400·CC-410을 선행으로 적지만
  이 항목의 네 기준 중 **어느 것도 provider를 필요로 하지 않는다.** 순서 선호를
  기술적 차단으로 읽으면 외부 대기가 UNE의 일까지 멈춘다 — D6에 적었다.

## 결정

### D1. 보안은 **전수**로 묻는다 — 고른 경로가 아니라 등록된 전부

항목마다 한두 경로를 골라 막히는지 보던 방식이 증명하지 못하는 것은 **아무도
고르지 않은 경로**다. 가드를 빠뜨린 라우트는 정확히 그 자리에 생긴다.

`listRoutes(app)`를 API 공개 표면에 두고 **런타임 라우터가 등록한 것 전부**를
훑는다. 소스를 정규식으로 읽지 않는 이유는 그것이 등록된 것이 아니라 적힌 것을
보기 때문이다 — 모듈에 넣지 않은 컨트롤러, 조건부 등록은 정규식에 잡히지 않는다.

다섯을 묻는다.

1. 토큰 없이 부르면 401인가(`@Public`만 예외).
2. 권한이 선언된 라우트를 그 권한 없는 사용자가 부르면 403인가. **403이 본문
   검증보다 먼저 서야 한다** — 400이 먼저면 권한 없는 사용자가 요청 형식을
   탐색할 수 있고, 404가 먼저면 자원의 존재가 샌다.
3. 다른 기관 토큰으로 자원 경로를 불러 2xx가 나지 않는가.
4. 멱등 키 없는 POST는 **다른 보호가 있는 것뿐**인가.
5. 권한을 선언하지 않은 라우트는 **의도된 것뿐**인가.

①②③은 전수 통과했다. ④⑤는 목록으로 고정하되 **사유를 함께** 적게 했다 —
목록을 지우고 통과시키는 것이 가장 쉬운 길이므로.

### D2. ④⑤의 목록은 **양방향**으로 본다

새 라우트가 목록에 없으면 걸리고, **사라진 라우트의 예외가 남아도** 걸린다.
후자가 없으면 목록이 낡아 "이건 왜 여기 있지"만 남는다. 실제로 이 방향이
작동했다 — 처음 적은 예외 둘이 틀렸고(`/auth/refresh`는 `@Public`이며
`GET /tasks`는 권한이 있다) 그 자리에서 드러났다.

④의 판단: 편집 계열(changeset·restore·autosave)은 멱등 키가 아니라
`If-Match` + `baseRevisionId` 낙관 잠금으로 보호된다. 그것이 **더 정확하다** —
두 번째 적용은 base가 움직여 409가 되고, 자동저장은 본래 last-write-wins라
멱등 키를 걸면 저장 자체가 막힌다. CLAUDE.md가 "편집은 Revision·ETag·ChangeSet"
이라고 적은 그대로다.

### D3. `live`와 `ready`를 가른다

`/health`가 언제나 `ok`를 돌려주던 것은 **프로세스가 떠 있다**만 말한다. DB가
죽어도 `ok`면 로드밸런서가 계속 요청을 보내고 사용자는 500을 받는다.

- `/health`·`/health/live` — 의존성을 보지 않는다. **liveness가 의존성에 걸리면
  DB 장애가 컨테이너 재시작 폭풍이 된다.**
- `/health/ready` — DB와 객체 저장소에 실제로 물어본다. 하나가 죽으면
  `degraded`와 **사유**를 낸다. 하나 죽었다고 전부를 실패로 적으면 어디가
  문제인지 말하지 못한다.
- 준비 점검은 **던지지 않는다.** 여기서 예외가 나면 500이 되고 "왜 준비가 안
  됐는지"를 잃는다 — 그것이 이 엔드포인트의 전부다.

### D4. 가림은 **나가는 길목에 한 번만**

`.claude/rules/backend.md`가 금지하는 것(토큰·개인정보 원문·문서 본문의 INFO
기록)을 각 호출 지점에 맡기면 언젠가 한 곳이 어기고, 어긴 것은 로그에 영구히
남는다. 구조화 로거가 **이름으로** 지운다 — 값의 모양으로 판정하면 놓친다.
본문·원문은 지우지 않고 **크기만 남긴다**: 지우는 것과 덜어내는 것은 다르고,
"얼마나 컸나"는 진단에 쓰인다.

### D5. 메트릭 라벨은 **경로 템플릿**이다

실제 경로를 라벨에 쓰면 UUID마다 시계열이 하나씩 생긴다(cardinality explosion).
더 나쁜 것은 **외부에서 시계열을 만들 수 있다**는 것이다 — 아무 경로나 호출하면
수집기 메모리가 는다. 매칭된 라우트만 쓰고, 매칭되지 않으면 `unmatched`로 접는다.

`prom-client` 같은 의존은 더하지 않았다. 필요한 것이 카운터 하나와 히스토그램
하나뿐인데 런타임 의존을 늘리면 SBOM과 취약점 추적 대상이 함께 는다.

### D6. 성능은 **기준선**이지 게이트가 아니다

설계에 상황·실행 조회 경로의 목표치는 없다. 그래서 실측을 등록하고 편집 목표치
300ms를 참고선으로 함께 적는다. 넘어도 테스트를 실패시키지 않는다 — 게이트로
만들면 다음 사람이 목표치를 낮춰 통과시킨다(CC-170이 세운 판단 그대로).

부하를 심고 잰다. 빈 상황을 재면 "아무것도 없을 때 빠르다"만 증명한다.

### D7. 백업은 **복구해 봐야** 백업이다

덤프를 뜨고, 빈 데이터베이스에 되돌리고, **원본과 대조**한 뒤 시간을 적는다.
대조는 행 수만 보지 않는다 — RLS가 켜진 테이블 수, FORCE, 정책, 트리거, 인덱스,
CHECK, FK, 마이그레이션 수를 함께 본다. **행만 세면 "데이터는 있는데 아무도 못
막는" 복구본을 통과시킨다.**

첫 실행이 실제로 결함을 잡았다. PATH의 `pg_dump` 18로 서버 16을 덤프하면 덤프에
`SET transaction_timeout`이 들어가고 복구가 첫 줄에서 죽는다. **대조가 없으면
"덤프는 떴다"로 끝난다.** 그래서 버전 선검사를 넣어 시작 전에 멈추고, 서버와
같은 버전의 도구(컨테이너 안의 것)를 쓰는 경로를 열었다.

실측: pg_dump 16 · 서버 16, **RTO 22.28초**(덤프 0.39s + 복구 21.89s),
스키마·정책 81·트리거 36·행 수 전부 일치.

## 수용 한계 (지금 하지 않은 것 / 지금 사실이 아닌 것)

1. **트레이스가 없다.** 수집기(OTLP 엔드포인트) 주소가 배포 환경에 딸린 값이고
   **OB-14가 아직 열려 있다.** 지금 붙이면 아무 데도 보내지 않는 계측만 남는다.
   요청마다 상관관계 ID가 있고 로그·메트릭이 같은 경로 라벨을 쓰므로, 수집기가
   생기면 **내보내는 쪽만** 붙이면 된다.
2. **백업 훈련의 RTO는 거의 빈 DB에서 잰 값이다.** 도메인 테이블 대부분이 0행
   이다(테스트는 일회용 DB를 쓴다). 실제 데이터량에서의 RTO는 다르며, 그 측정은
   운영 데이터가 있는 환경에서 다시 해야 한다.
3. **오브젝트 저장소는 훈련 대상이 아니다.** DB만 덤프·복구한다. MinIO/S3 버킷
   미러링은 저장소 계정과 대상 버킷이 배포 결정(OB-14)에 딸려 있다. 문서
   산출물이 DB 밖에 있으므로 **복구본은 메타데이터만 온전하다.**
4. **성능 기준선은 단일 프로세스·인메모리 저장소에서 잰 값이다.** 네트워크
   지연, 실 MinIO, 동시 사용자가 없다. 부하 시험(동시성)은 이 항목에 없다.
5. **롤은 덤프에 없다**(클러스터 수준). 다른 서버로 옮기는 절차는 initdb와
   마이그레이션 0050이 먼저 서야 한다 — 훈련 보고서가 그 사실을 매번 적는다.
6. **워커의 로그는 아직 console.\*이다.** 로거는 API 패키지에서 공개했으므로
   워커가 쓸 수 있으나, 이 항목에서 바꾸지 않았다. 워커 로그가 구조화되지
   않으면 잡 실패를 상관관계로 추적할 수 없다 — 후속.
