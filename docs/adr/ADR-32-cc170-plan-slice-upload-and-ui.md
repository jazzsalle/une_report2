# ADR-32: CC-170 계획서 수직 슬라이스 — 업로드 진입점·최소 UI·성능 기준선

- 상태: ACCEPTED (2026-08-05, CC-170)
- 관련: 설계 09(화면·상태·권한·오류), 설계 10 §2(파일 3단 업로드)·§3.4(UNE-DOC-001~004),
  `tests/baseline/e2e-test-scenarios.md` E2E-PLAN-001, ADR v1.1 §G15-5(성능),
  **ADR-29(D4/D11)**, **ADR-30(D2)**, **ADR-31(D1/D5/D6/D9/D12)**,
  `.claude/rules/{backend,frontend,security,architecture,testing,hwpx}.md`
- 범위: 업로드·반입 HTTP 진입점, 슬라이스 UI, 슬라이스 E2E, 성능 기준선.
  실제 T3Q SSO(OB-01)와 rhwp 편집기(OB-12)는 밖 — 근거는 D12·D13.

## 배경: 인수기준이 요구한 경로에 진입점이 없었다

CC-170의 인수기준은 "SSO mock to HWPX download"인데, 착수 시점에 그 경로는
**HTTP로 걸을 수 없었다**.

- `UNE-DOC-001~004`(파일 사전등록·업로드 완료·HWPX 반입·분석조회)는 계약에
  `GenericRequest/GenericResponse` 자리표시자로만 있었고 컨트롤러가 없었다.
  ADR-31 D1이 "별도 화면 흐름"이라며 CC-160 범위에서 제외했고, 그 뒤로 아무
  항목도 가져가지 않았다.
- `DocumentImportService`는 존재했지만 컨트롤러에 배선되지 않아 테스트만
  직접 호출했다.
- `apps/web`은 4개 파일 셸이었다. 화면이 없으면 "화면 캡처"라는 필수증거도 없다.

그래서 CC-170은 통합·QA 항목이 아니라 **진입점을 만드는 구현 항목**이 됐다.

---

## D1. 업로드는 설계대로 3단으로 만든다

**결정**: 사전등록(UNE-DOC-001) → 직접 전송 → 완료확정(UNE-DOC-002)을 그대로
구현한다. 바이트는 정상 경로에서 API를 지나가지 않는다.

**근거**: 설계 10 §2가 "사전등록→직접 업로드→완료확정"이다. 바이트를 API가
중계하면 큰 파일에서 API가 병목이 되고, 업로드 진행률·재시도·재개 같은
문제를 전부 API가 떠안는다. 저장소가 이미 잘하는 일이다.

**대가**: 검증 시점이 전송과 분리된다. 그래서 D2가 필요하다.

## D2. 검증 지점은 UNE-DOC-002 하나다

**결정**: 완료확정에서 **저장된 바이트를 읽어** ① 크기 ② SHA-256 재계산
③ 내용 기반 형식(ZIP 매직 + `mimetype` 엔트리, 엔진의 `analyzePackage` 재사용)을
사전등록 선언과 대조한다. 하나라도 어긋나면 422이고 행은 `ABORTED`로 끝난다.

**근거**: 검사가 두 곳에 있으면 둘이 갈라지고, 갈라진 뒤에는 어느 쪽이 진실인지
알 수 없다. 전송 라우트는 저장만 하고 판단하지 않는다. 확장자·`Content-Type`은
근거가 아니다(`.claude/rules/security.md`).

**보강**: presign URL에는 선언 해시를 **서명에 넣는다**(`x-amz-checksum-sha256`).
저장소가 다른 바이트를 직접 거부하므로, 검증되지 않은 바이트가 애초에 자리에
놓이지 않는다. 실 MinIO에서 확인했다.

## D3. 업로드 검증은 악성코드 검사와 **다른 축**이다

**결정**: `file_object.upload_state`(PENDING/VERIFIED/ABORTED)를 0022로 신설한다.
`scan_status`는 그대로 두고 **PENDING으로 남긴다**.

**근거**: AV 스캐너가 없다(OB-15). 검증을 통과했다고 `scan_status='CLEAN'`으로
올리면 하지 않은 검사를 했다고 감사에 기록하게 된다. 두 축을 한 컬럼에 밀어
넣으면 그 거짓말이 구조가 된다.

**부수**: "전송 완료"를 상태로 두지 않는다. 검증하지 않은 '올라옴'은 이후 어떤
결정의 근거도 되지 못하므로 도달 가능한 상태만 늘린다.

## D4. `malware_scan` 테이블을 만들지 않고 계약을 고친다

**결정**: UNE-DOC-002의 `x-db-tables`에서 `malware_scan`을 뺀다. 그 테이블은
**어떤 마이그레이션에도 없었다**.

**근거**: 계약이 존재하지 않는 테이블을 가리키면 `x-db-tables`는 검증 가능한
사실이 아니라 장식이 되고, 다음 사람은 그것을 근거로 설계를 읽는다. 스캐너가
없는 상태에서 결과 테이블을 만들면 영구히 빈 테이블이 남는다. ADR-29가
`prototype_registry` → `style_prototype` 이름 드리프트를 구현 진실로 종결한
것과 같은 판단이다.

**재발 방지**: `tests/contract/src/file-upload.contract.test.ts`가 **구현된
API**(컨트롤러 주석의 API ID에서 유도)의 `x-db-tables` 전건을 데이터 사전과
대조한다. 손으로 관리하는 목록은 낡으므로 유도한다.

## D5. 업로드 키는 `sources/` 아래에서 `fileId`로 격리한다

**결정**: `tenants/{tenantId}/sources/{fileId}/{sha256}.hwpx`. 검증 전 바이트를
내용 주소 키(`sources/{sha256}`)에 올리지 않는다.

**근거**: 그 시점의 해시는 클라이언트의 **주장**이다. 검증되지 않은 바이트를
내용 주소에 올리면 "키가 곧 내용"이라는 전제가 깨지고, 같은 해시를 선언한 다른
흐름이 서로의 바이트를 보게 된다.

**접두사 정정(리뷰 M-4)**: 처음에는 `uploads/`로 두었다. 그러나 검증을 통과한
이 객체는 문서의 **영구 원본**이 되어 보존 Export가 계속 읽는다 — 승격(복사)
경로를 만들지 않기로 했으므로, `uploads/`라는 이름은 수명주기 규칙이나 정리
배치에 "스테이징"으로 읽혀 문서의 유일한 원본을 지울 수 있다. CC-160이
`source_file_id` NULL로 이미 겪은 실패 유형이다. 내용 주소 중복 제거를 잃는
대가는 받아들인다 — 같은 파일을 두 번 반입하는 것은 드물고, 이름이 수명을
거짓으로 말하는 편이 훨씬 위험하다.

## D6. presign 불가 어댑터는 예외가 아니라 `null`을 돌려준다

**결정**: `ObjectStoragePort.presignPut`은 능력이 없으면 `null`이다. 호출자(API)가
자기 전송 라우트(`PUT /files/{fileId}/content`)로 대체한다.

**근거**: 능력 질문에는 능력으로 답한다. 대체 경로를 고르는 일은 자기 URL을 아는
호출자의 몫이다. 인메모리 어댑터가 흉내낸 URL을 돌려주면 클라이언트가 쓸 수 없는
주소를 받고 실패가 업로드 단계로 미뤄진다.

**전송 라우트의 성질**: presign URL과 같아야 한다 — **Bearer 없이** 서명된
티켓만으로 인가한다. 티켓은 **확정 전에는 재전송할 수 있다**(전송 실패의 재시도
경로다). 확정 후에는 409다. 초기 기술은 "1회용"이었으나 구현은 그렇지 않았고,
계약·문서를 구현 사실에 맞췄다(리뷰 M-1). 그래야 화면 코드가 드라이버에 따라 갈라지지 않는다.
티켓의 테넌트 claim으로 RLS 스코프를 열기 때문에 RLS 우회 경로를 만들지 않는다.
서명 키는 JWT 키에서 라벨로 파생한다(프로토콜 혼동 방지).

**카탈로그 밖**: 이 라우트에는 `x-une-api-id`를 붙이지 않는다. 설계 10 §3.4의
카탈로그에 없는 것을 있는 것처럼 만들면 카탈로그가 사실이 아니게 된다.

## D7. presign 주소는 **브라우저가 보는 주소**로 서명한다

**결정**: `OBJECT_STORAGE_PUBLIC_ENDPOINT`를 실제로 읽어 presign 전용 클라이언트를
만든다.

**근거**: 이 변수는 CC-001부터 `.env.example`에 "presigned URL에 들어가는
엔드포인트"로 적혀 있었지만 **읽는 코드가 없었다** — presign 경로가 없었기
때문이다. API가 `http://minio:9000`으로 저장소를 보고 브라우저는
`http://localhost:9000`으로 봐야 하는 배포에서, 서명된 URL은 브라우저에서 연결조차
되지 않는다. SigV4는 Host를 서명하므로 브라우저가 보낼 Host로 서명해야 한다.

## D8. 반입은 동기다

**결정**: UNE-DOC-003은 분석을 동기로 끝내고 결과를 응답에 싣는다. 설계의
"Document+AnalysisJob"에서 Job 형태를 취하지 않는다.

**근거**: 측정 결과다. 실문서 6종 분석이 수십 ms이고 합성 50쪽이 p95 256ms다.
Job으로 만들면 상태 폴링·리스·재시도를 관리할 대상이 하나 늘어나는 대신 사용자가
기다리는 시간은 같다.

**되돌릴 조건**: 대용량에서 분석이 G15-5 목표(P95 5초)를 넘기면 그때 Job으로
바꾼다. 응답 형태는 이미 `analysis`를 담고 있으므로 Job 결과로 옮기면 된다.

## D9. `document.plan_id`를 만들지 않는다 — `plan.document_id`가 이미 있다

**결정**: 역방향 링크를 새로 만들지 않는다. UNE-DOC-003이 `plan.document_id`를
채운다. 0022는 대신 **부분 유니크 인덱스**로 "한 문서를 두 계획서가 주장할 수
없다"를 세운다.

**근거**: `plan.document_id`는 0003부터 있고 FK도 0007에 있으며 plan 저장소가 이미
읽어 응답에 싣는다 — **값을 쓰는 경로만 없었다**. 같은 관계에 진실을 둘 두면
반드시 갈라진다. (계획 단계에서는 `document.plan_id`를 세우려 했고, 구현 중
기존 컬럼을 발견해 뒤집었다.)

## D10. 화면은 만들되 편집기는 만들지 않는다

**결정**: `apps/web`에 여섯 단계 스테퍼(로그인 → 계획서 → 기준정보 → HWPX 반입 →
목차·본문 생성 **+ 실체화** → Export·다운로드)를 만든다. **문서 편집기 화면은 없다.**

**실체화 단계(5-3)는 뒤늦게 추가했다**(리뷰 QA 필수3). 처음에는 생성 다음이 곧장
Export였고, 그래서 화면으로 내려받은 HWPX에는 생성 본문이 한 글자도 없었다 —
업로드한 원본 그대로였다. 인수기준이 "SSO부터 HWPX 다운로드까지"인데 그 다운로드가
원본이라면 증거가 인수기준보다 약하다. 삽입 자리는 화면이 고른다(정적영역 밖의
마지막 문단 뒤 — 수용 한계 1).

**근거**: 인수기준의 "screen evidence"는 화면 없이는 충족할 수 없다. 반면 편집기는
rhwp 미반입(OB-12)으로 원천 불가다. 본문을 사람이 손으로 고치는 화면은 rhwp가
들어오는 항목에서 생긴다.

**규칙**: 신규 런타임 의존성 0(라우터도 넣지 않는다 — 화면 증거에 필요한 것은
구분되는 상태뿐이다). 타입은 계약에서 생성한다(`apps/web/src/generated`) —
화면이 응답 모양을 손으로 적으면 드리프트가 사용자 화면에서만 드러난다.
서버 오류 메시지를 다시 쓰지 않고 "다음 행동"만 더한다. 토큰은 메모리에만 둔다.

## D11. CORS는 명시 목록만 허용한다

**결정**: `UNE_CORS_ALLOWED_ORIGINS` 환경변수의 출처만 허용하고 와일드카드는
**기동에서 거부**한다. `credentials`는 켜지 않는다(토큰은 Authorization 헤더).

**근거**: 허용 출처는 배포마다 아는 값이다. 모르는 채로 열어 두는 편의는 나중에
그대로 운영에 남는다.

## D12. 슬라이스 E2E는 한 프로세스에서 API와 워커를 함께 돌린다

**결정**: `tests/e2e`(@une/e2e)를 신설하고 `createApp`과 워커 러너를 같은
프로세스에서 구동한다. 워커에 `src/index.ts` 공개 표면을 만든다.

**근거**: 두 프로세스로 띄우면 테스트가 프로세스 감독까지 하게 되고, 실패했을 때
"무엇이 죽었나"가 먼저 문제가 된다. 여기서 증명할 것은 프로세스 배치가 아니라
**경로가 이어진다**는 것이다.

**편집 단계의 대역**: E2E-PLAN-001의 "rhwp 편집"은 편집기가 없으므로 **본문
실체화(materialize)**가 대신한다 — 그것이 지금 문서를 실제로 바꾸는 유일한
경로이고, 되쓰기·Track A·다운로드를 모두 태운다.

## D13. 화면 캡처는 CI 게이트가 아니다

**결정**: `pnpm --filter @une/e2e screens`가 브라우저로 여섯 화면을 걸으며 PNG를
남긴다. CI에서는 돌리지 않는다.

**근거**: 브라우저 바이너리(약 120MB)를 CI가 매번 받게 하는 비용이 얻는 것보다
크다. 분담을 명시한다: **UI 로직은 vitest**, **경로는 API E2E**, **캡처는 증거**.
캡처가 회귀를 잡지 못한다는 사실을 증거 문서에 적는다.

## D14. 성능 기준선은 합성 50쪽으로 재되, 게이트로 만들지 않는다

**결정**: 실문서를 원본으로 두고 문단만 2,000개까지 늘린 합성 문서를 테스트
시점에 결정적으로 만들어 측정한다. 목표 미달이어도 테스트를 실패시키지 않는다.

**근거**: 보유 코퍼스는 23KB~500KB 소형 6종뿐이라 "일반 50쪽"을 잴 수 없다.
처음부터 합성하면 실문서의 병리(run 구성, 표, 정적영역)가 사라져 낙관적인 수치가
나온다. 그리고 성능 테스트를 게이트로 만들면 다음 사람이 목표치를 낮춰 통과시킨다 —
판정은 증거 문서와 리뷰가 한다.

**가정**: 문단 40개 = 1쪽. 우리는 렌더하지 않으므로(설계 07 §1.1) 실제 쪽 수는
한/글이 정한다. 이 환산은 가정이며 그렇게 기록한다.

## D15. 슬라이스가 밟은 되쓰기 결함 3건은 엔진에서 고친다

CC-160은 문단을 **하나** 넣는 경우만 시험했다. 실체화는 한 번에 여럿을 넣는다.
E2E가 처음 그 경로를 밟아 셋을 드러냈고, 셋 다 "테스트를 피해 가는" 대신
엔진을 고쳤다.

| # | 결함 | 조치 |
|---|---|---|
| 1 | 두 번째부터의 `anchorHint`가 AUTHORED 문단을 가리켜 되쓰기가 거절 → **실체화한 문서는 통째로 Export 불가** | 체인을 거슬러 원본 문단까지 따라간다. 순환은 거부 |
| 2 | 되쓰기가 앵커 이웃을 복제해 실행기가 고른 프로토타입(§1.7)이 무시됨 → 재분석 시 RTA-STY-001 FAIL | **서식은 IR이 정한다** — 의도한 서식과 같은 문단을 복제하고, 없으면 거부 |
| 3 | 실문서 OUTLINE_1 프로토타입은 run 4개 + 빈 run이라 복제기가 거절 | 텍스트를 첫 run에 모으고 나머지 텍스트 run은 비운다. 빈 run은 그대로. 탭·인라인 컨트롤이 섞이면 여전히 거부 |

## D16. 편집 경로의 Track A는 LIMITED가 정상이다

**결정**: 문단을 넣으면 `RTA-STY-002`(개요 수준)가 WARN을 내고 보고서는
LIMITED가 된다. 바이트는 나간다.

**근거**: 삽입은 뒤쪽 문단의 개요 서수를 민다. 손상이 아니라 편집의 정상적
결과다. FAIL이면 폐기다(ADR-31 D6) — WARN과 FAIL의 구분이 그래서 중요하다.
