# 1. 문서 개요 및 통제 원칙

## 1.1 목적

• 재난안전계획서 생성도구의 사용자가 시스템에 접속하여 임의 HWPX 양식을 분석하고, 기준정보를 입력하며, T3Q RPT-001/002로 목차·본문을 생성하고, rhwp 중앙 편집 Surface에서 직접 및 AI 보조 편집을 수행한 후 HWPX/PDF/DOCX를 산출하는 전 과정을 구현·시험 가능한 수준으로 정의한다.

• 각 시나리오는 Actor, 사전조건, Trigger, 입력, 정상흐름, 대체흐름, 예외, 권한, 상태, 데이터, 화면/API 후보, 감사증거, 인수기준, 요구사항·ADR·WBS·E2E 추적을 한 건으로 관리한다.

• 본 문서는 화면설계와 API/DB/Sequence를 대체하지 않는다. 다만 후속 상세설계가 누락 없이 파생될 수 있도록 화면·연계·데이터 경계를 식별한다.

## 4.2 상태 모델

| **대상**          | **상태 흐름**                                                                                                                    | **불변/통제**                                       |
|-------------------|----------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------|
| Document          | DRAFT → TEMPLATE_PENDING → CONTEXT_READY → OUTLINE_REVIEW → CONTENT_GENERATING → EDITING → REVIEW_REQUESTED → FINALIZED/ARCHIVED | FINALIZED는 불변 artifact를 갖고 변경은 새 revision |
| Template Analysis | UPLOADED → VALIDATING → ANALYZING → CONFIRM_REQUIRED/CONFIRMED/LIMITED/REJECTED                                                  | REJECTED는 생성 진입 불가                           |
| Outline           | NONE → GENERATING → REVIEW → EDITING → CONFIRMED → REGEN_DIFF                                                                    | 확정 revision이 본문 Job 입력                       |
| Generation Job    | QUEUED → RUNNING → CANCEL_REQUESTED → STOPPED/PARTIAL/COMPLETED/FAILED                                                           | 늦은 이벤트는 cutoff 이후 적용 금지                 |
| Block Edit        | GENERATING → GENERATED → USER_EDITED/LOCKED → DIFF_PENDING → APPLIED/REJECTED/ERROR                                              | USER_EDITED/LOCKED 자동덮어쓰기 금지                |
| ChangeSet         | DRAFT → VALIDATING → READY → APPLIED/REJECTED/CONFLICTED/ROLLED_BACK                                                             | APPLIED만 문서 revision 증가                        |
| Export            | REQUESTED → QUEUED → PROCESSING → VALIDATING → COMPLETED/FAILED                                                                  | Track A 실패는 다운로드 금지                        |

## 4.3 상태 전이 공통 규칙

• 모든 상태변경은 서버에서 권한·현재상태·baseRevision을 검증한 후 수행하며 클라이언트 표시만으로 상태를 확정하지 않는다.

• 외부 Provider 응답은 ProviderEvent/Proposal 상태를 거쳐 Contract 검증과 ChangeSet 적용 전에는 DocumentState를 변경하지 않는다.

• 오류상태에서도 원본 SourceArtifact, 마지막 정상 DocumentRevision, 사용자 수정 Block, 감사로그를 삭제하지 않는다.

• 상태전이는 Scenario ID와 correlationId를 포함한 AuditEvent를 생성한다.

## 10.2 인수 완료조건

• 필수 Scenario의 정상·대체·예외 흐름과 대응 E2E가 PASS이며 결함/제한사항이 승인되어야 한다.

• T3Q 실제 RPT-001/002 계약·샘플·오류·인증 Gate가 통과하지 않으면 Mock E2E만으로 운영 인수를 선언하지 않는다.

• RC는 Track A와 고정 한컴 환경 Track B를 모두 통과해야 배포 승인된다.

## A.1 실행 절차

**1.** SSO 진입 후 신규문서와 기관 HWPX 양식을 등록한다.

**2.** Template Analyzer가 제목·개요·본문·표 Prototype을 판정하고 저신뢰 항목을 확인한다.

**3.** 태풍·호우/예방·대비 기준정보와 출처규칙을 입력해 Snapshot을 만든다.

**7.** 근거를 확인하고 HWPX Track A 저장·PDF 보조 Export를 수행한다.

**2.** 저신뢰 통계표/주석 역할을 사용자 확인해 Template Profile을 확정한다.

**3.** 감염병 발생현황·보고일·필수통계·관계기관 계획을 기준정보로 입력한다.
