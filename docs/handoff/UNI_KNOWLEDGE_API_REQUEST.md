# UNI 지식문서 API 규격 요청 — 사내 개발자용 설명서

작성 2026-08-09 · 대상 `contracts/openapi/uni-knowledge-api-change-request-v1.yaml` ·
관련 ADR-36, OB-13

---

## 0. 이 문서를 먼저 읽어야 하는 이유

같이 붙은 YAML은 **규격**입니다. 이 문서는 **왜 그 규격인지**입니다.

받으시는 분은 UNE 쪽에서 무엇을 만들고 있는지 모르실 가능성이 큽니다. 그래서
"어느 필드를 알려달라"는 요청만 드리면 왜 그게 필요한지, 왜 저희가 그냥
적당히 맞춰 쓰지 않는지 이해하기 어렵습니다. 먼저 그림부터 설명드립니다.

**요청드리는 것은 크게 두 가지입니다.**

1. **지금 당장 필요한 것 두 개** — `/documents/upload`의 multipart 파일 파트
   이름, `/auth/login` 응답의 토큰 필드 이름. 이 둘만 있으면 저희가 이미
   작성한 연동 코드가 실제로 동작합니다. (§4)
2. **정식으로 맞춰 주셨으면 하는 규격** — 나머지는 YAML에 적었습니다.
   지금 없어도 진행은 되지만, 있으면 오류 처리와 중복 처리를 제대로 할 수
   있습니다. (§5)

## 1. UNE가 만들고 있는 것

재난 상황에서 쓰는 **문서 작성·대응 플랫폼**입니다. 크게 세 갈래입니다.

| 갈래 | 하는 일 |
|---|---|
| 상황 관리 | 기상청·행안부 등에서 재난 상황 정보를 모아 사용자가 확인한 **확정본**을 만든다 |
| 계획서 생성 | 확정본을 근거로 T3Q의 LLM이 보고서 초안을 만들고, UNE가 HWPX로 편집·출력한다 |
| SOP(대응절차) | 훈련·매뉴얼 자료를 근거로 대응 절차를 만들고 실행·기록한다 |

**UNI가 들어오는 자리는 세 번째입니다.** 훈련계획서·기관 매뉴얼·평가지침
같은 문서를 UNI에 등록해 두고, 나중에 SOP를 만들 때 그 문서들에서 근거를
검색합니다. UNI의 RAG가 그 역할을 합니다.

이번에 만든 부분(내부 코드 CC-220)은 그중 **"문서를 UNI에 등록하고 학습
상태를 추적하는 것"**까지입니다. 검색은 다음 단계입니다.

## 2. UNE가 UNI를 부르는 방식 — 세 가지 원칙

### 2.1 화면(브라우저)은 UNI를 직접 부르지 않습니다

전부 UNE 백엔드를 거칩니다. UNE 백엔드가 JWT를 붙이고, 접근 로그를 남기고,
기관별 권한을 확인한 뒤 UNI를 호출합니다. 그래서 UNI 입장에서 보이는
호출자는 항상 UNE 서버 한 곳입니다.

### 2.2 업로드는 사용자를 기다리게 하지 않습니다

사용자가 파일을 올리면 UNE는 **접수만 하고 즉시 응답**합니다. 실제 UNI 호출은
백그라운드 워커가 합니다. 파일 업로드에 60초까지 걸릴 수 있는데 그동안 화면을
묶어 둘 수 없기 때문입니다.

그래서 UNE 안에서 문서 상태가 이렇게 흐릅니다.

```
등록 접수 → (워커가 UNI 호출) → UNI가 doc_id 반환 → 주기적으로 처리상태 확인
```

### 2.3 UNI가 알려준 것과 UNE가 아는 것을 **따로** 기록합니다

이게 설계상 중요한 부분입니다. UNE는 상태를 **두 칸**에 나눠 저장합니다.

| 칸 | 뜻 | 값 |
|---|---|---|
| UNE 등록 상태 | 우리가 파일을 검사했고 UNI에 보냈는가 | 전송대기 / 전송중 / 등록됨 / 실패 / 취소 |
| UNI 처리 상태 | UNI가 파싱·색인을 어디까지 했는가 | QUEUED / PARSING / INDEXING / REFERENCE_GENERATING / READY / ERROR |

**UNI 처리 상태가 비어 있다는 것은 "아직 모른다"는 뜻이지 "처리 안 됐다"가
아닙니다.** 이 구분이 없으면 UNI가 응답하지 않을 때 무엇이 참인지 말할 수
없게 됩니다. 감사(監査)를 받는 시스템이라 "확인하지 않은 것"을 "확인해서
아니었다"로 적으면 안 됩니다.

여기서 UNI 쪽에 부탁이 하나 생깁니다 — **처리 상태 문자열을 임의로 늘리지
말아 주십시오.** UNE는 위 여섯 값만 받아들이고 모르는 값이 오면 저장하지 않고
거부합니다(원문은 남깁니다). 추측해서 저장하면 그 값이 나중에 "이 문서를 SOP
근거로 써도 되는가" 판정까지 흘러갑니다. 값을 추가해야 하면 미리 알려 주시면
됩니다.

## 3. 왜 저희가 "알아서 맞춰 쓰지" 않는가

이 부분을 특히 이해 부탁드립니다.

저희가 받은 UNI API 명세 파일에는 25개 엔드포인트의 **요청·응답이 전부
`additionalProperties: true`**로만 되어 있습니다. 쉽게 말해 "객체가 온다"는
것 외에는 아무 정보가 없습니다. 경로와 인증 방식은 알 수 있지만 필드 이름은
하나도 알 수 없습니다.

그래서 저희는 두 가지 선택지가 있었습니다.

- **(A) 흔한 이름으로 찍어서 보낸다** — `file`, `access_token` 등
- **(B) 설정값으로 빼고, 값이 없으면 아예 기동하지 않게 한다**

**(B)를 골랐습니다.** 이유는 (A)가 만드는 실패 모드가 나쁘기 때문입니다.
파일 파트 이름을 틀리게 보내면 UNI는 422를 돌려줄 텐데, 그 422를 보고
운영자는 "UNI가 거절했다"고 읽습니다. 실제로는 UNE가 잘못 보낸 것입니다.
원인이 엉뚱한 곳을 가리키면 디버깅이 몇 배로 길어집니다.

로그인 토큰도 같습니다. 응답에서 아무 문자열이나 찾아 토큰으로 쓰면, 그게
토큰이 아닐 때 그 뒤에 나오는 모든 401의 원인이 숨습니다.

그래서 **현재 UNE의 실제 연동 코드는 완성되어 있지만 켜면 기동을 거부합니다.**
필드 이름 두 개가 설정에 없기 때문입니다. 그 두 개만 주시면 코드 수정 없이
바로 붙습니다.

## 4. 지금 바로 필요한 것 두 가지

### 4.1 `/documents/upload`의 multipart 파일 파트 이름

저희가 아는 것(설계 문서 기준):

```
POST /documents/upload?uploader=...&force=false   (multipart, JWT 필요)
→ {message, filename, doc_id}
```

모르는 것: **파일을 담는 파트의 이름**. `file`인가요? 다른 이름인가요?
메타데이터를 함께 받는 파트가 따로 있나요?

가장 도움이 되는 형태는 **실제로 성공한 요청 예시 한 벌**입니다.
`curl` 명령 한 줄이면 충분합니다. 예:

```bash
curl -X POST 'http://<host>/documents/upload?uploader=test&force=false' \
  -H 'Authorization: Bearer <token>' \
  -F '<이 부분이 궁금합니다>=@sample.pdf'
```

### 4.2 `/auth/login` 응답의 토큰 필드 이름

저희가 아는 것: 요청은 `{username, password}`이고 이후 `Bearer` 방식으로
쓴다는 것.

모르는 것: **응답 JSON에서 토큰이 담긴 필드 이름**, 그리고 만료 정보가
있다면 그 형태.

이것도 **실제 응답 예시 한 벌**이면 충분합니다. 토큰 값 자체는 가려 주셔도
됩니다 — 필드 이름만 알면 됩니다.

```json
{ "??????": "eyJhbGciOi...", "??????": 3600 }
```

## 5. 정식으로 맞춰 주셨으면 하는 것

YAML에 `CR-UNI-00x` 번호로 적어 두었습니다. 요약하면 이렇습니다.

| 번호 | 내용 | 왜 필요한가 |
|---|---|---|
| CR-UNI-001 | 로그인 응답 스키마 확정 | §4.2 |
| CR-UNI-002 | 업로드 multipart 규격 확정 | §4.1 |
| CR-UNI-003 | 처리상태 조회 경로·응답 확정, **ERROR 사유 필드 추가** | 사용자에게 "왜 실패했는지" 못 보여주면 재시도할지 뺄지 판단할 수 없습니다 |
| CR-UNI-004 | `force=false`일 때 중복이면 **기존 doc_id를 함께 반환** | 아래 §6에서 설명드립니다 — 저희에게 꽤 중요합니다 |
| CR-UNI-005 | 파일 크기 상한·허용 형식 목록 | 지금은 UNE가 자체 기준으로 먼저 거르는데, UNI 기준과 다르면 UNE를 통과한 파일이 UNI에서 떨어집니다 |
| CR-UNI-006 | 참조요약(`/reference`) 200 응답 스키마 | 저희는 보관만 하므로 형태만 알면 됩니다 |
| CR-UNI-007 | 안정적인 오류코드 체계 | 지금은 HTTP 상태로만 분기해서 "재시도하면 되는 실패"와 "고쳐야 하는 실패"를 정확히 못 가릅니다 |

## 6. 중복 업로드 문제 — 가장 상의드리고 싶은 부분

업로드 API에 **멱등키(idempotency key)가 없습니다.** 명세에도 설계 문서에도
그런 필드가 없습니다.

이게 왜 문제가 되냐면:

1. UNE가 파일을 UNI에 보냅니다.
2. UNI가 처리는 정상적으로 했는데, 응답이 오는 도중 네트워크가 끊깁니다.
3. UNE는 **성공했는지 실패했는지 알 수 없는** 상태가 됩니다.
4. 재시도하면 → UNI에 같은 문서가 **두 벌** 생깁니다.
5. 나중에 SOP 근거를 검색하면 같은 내용이 두 번 나옵니다.

현재 UNE는 이 상황을 "부작용 불확실"로 표시해 두고 **자동 재시도를 하지
않습니다.** 사람이 화면에서 보고 판단하게 합니다. 안전하지만 번거롭습니다.

**해결 방법 두 가지 중 하나면 됩니다.**

- **(가) `force=false`일 때 내용 해시로 중복을 판정하고 기존 `doc_id`를
  200이나 409로 돌려주기** — 이러면 재시도가 안전해집니다. 이미 있으면 기존
  것을 알려줄 뿐이니까요. **저희는 이 방식을 선호합니다.**
- **(나) 요청에 멱등키 헤더를 받아 같은 키면 같은 결과를 돌려주기**

UNI 쪽에서 이미 (가)처럼 동작하고 있을 수도 있습니다. 그렇다면 그 사실만
확인해 주셔도 됩니다.

## 7. UNE가 UNI에 하지 않을 것들

혹시 오해가 없도록 명시합니다.

- **계획서(보고서) 생성에는 UNI를 쓰지 않습니다.** 그쪽은 T3Q 담당이고,
  UNE 코드에 UNI 폴백이 없다는 것을 자동 검사로 강제하고 있습니다.
- **UNI에 올린 문서를 UNE가 임의로 삭제하지 않습니다.** 삭제·승격은 별도
  승인 절차를 거칩니다.
- **기관 공용 자료로 자동 승격하지 않습니다.** 사건 단위 보존이 기본입니다.
- **UNI 응답을 사실로 확정하지 않습니다.** UNI가 준 처리상태는 "UNI가 그렇게
  말했다"로 기록되고, 원본 응답도 함께 보관합니다.

## 8. 답을 주시는 방법

가장 편하신 형태면 됩니다. 우선순위는 이렇습니다.

1. **§4의 두 가지** (파일 파트 이름, 토큰 필드 이름) — 예시 한 벌씩이면
   충분하고, 이것만으로 저희 연동이 살아납니다.
2. §5의 CR 항목들 — YAML을 직접 고쳐 주셔도 되고, 메일로 "이건 이렇게
   동작한다"만 알려 주셔도 저희가 반영합니다.
3. §6의 중복 처리 — 현재 동작이 어떤지만 알려 주시면 됩니다.

UNE 쪽 담당 파일: `contracts/openapi/uni-knowledge-api-change-request-v1.yaml`
(규격), 이 문서(배경). 질문은 언제든 편하게 주십시오.
